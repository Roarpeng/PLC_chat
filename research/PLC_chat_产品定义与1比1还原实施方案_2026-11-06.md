## 0. 执行摘要

**产品是什么**：PLC_chat 不是 Web IDE、不是 TIA 替代品，而是「**PLC 逻辑前置设计器**」—— 在浏览器里把「有哪些设备、设备怎么跑、工站之间怎么配合」讲到完全清楚，一键导出**西门子 AF 架构版本的 TIA 工程骨架**；**具体硬件组态（型号、订货号、槽位、绝对地址）明确外包给 TIA 补全**。

**三条需求如何收敛**：
1. 前端构建项目 → 新建向导先定 PLC + 外围设备的**逻辑占位拓扑**；
2. 项目内对话（自然语言 + 上传资料）→ Canvas 渲染执行单元、工站交互逻辑 → 可手动编辑工站/执行件 → 画布同步回写逻辑；
3. 完全确认设备逻辑后 → **一键导出 AF 架构 TIA 项目，且 1:1 完全还原 canvas 逻辑**。

**第 3 条最硬**：这不是功能，是**契约级验收口径**。它要求「无丢失、无臆造、可证明」，因而倒逼第 1、2 条的架构必须建立在「单一权威源 + 受控写入 + 可追溯映射 + 双向等价校验」之上。当前项目的骨架已具备约六成，但**画布不是完整权威源、生成是重新规划而非逐项映射、且没有任何还原度校验** —— 这三点不解决，1:1 无从谈起。

**八条拍板口径**（用户按推荐统一确认）：机器可判定的 `fidelity_report`／框架基线白名单+哈希锁定／导出分「工程包」与「真机写入编译」两步／逻辑拓扑进 `spec_hash`／AF 档位先实测再定／允许增删改工站与执行件／DB-IO 上传改为可选补充／现在出完整方案。

**最终验收口径（三层，须同时通过）**：
`fidelity_ok`（逻辑语义等价）∧ `compile_ok`（TIA V19 编译零错误）∧ `reproducible`（同规格两次生成产物一致）。

**最重要的五个结论**：
1. 你找的对标物 CODESYS 4 是「**推出**」不是「退出」；但真正同构且有威胁的是**西门子 Eigen Engineering Agent** —— 官方已做到「自然语言描述机器 → 几分钟生成遵循 Siemens Automation Framework 的标准项目 → 直接在 TIA Portal 打开」，已 GA、19 国 100+ 企业。([西门子新闻稿](https://assets.new.siemens.com/siemens/assets/api/uuid:7c20b450-d7b7-4e8b-9a02-cb4bde2c520c/HQCOPR202604187387EN.pdf))
2. 因此**不做「类似 CODESYS 4 的 Web IDE」**，护城河押在厂商没有的「人在回路确认硬门禁 + 规格冻结 + 可复现证据链」。
3. 「1:1」必须定义为**逻辑语义 1:1**，而非对象逐字节 1:1 —— TIA Openness 的 OB 编号算法分配、实例 DB 不自动创建、LAD/FBD 只能模板法等是硬限制。
4. **AF 档位是唯一可能改变技术路线的未决项**：SIOS 109817223 官方 AF 以软件单元为标准实现，你的 PRD 选文件夹版；Eigen 称生成遵循 AF 的标准项目。二者兼容性**无直接证据，必须真机实测**。
5. 「Greenfield 生成链 TIA V19 编译零错误」目前**没有闭环证据**（`compile_ok` 含 warning 判定、`xml_package_unverified: True`、README「真机全绿」实为存量 HR001 链）。

### 1.3 理想交互链路（确认版）

| 步 | 用户动作 | 系统输出 | 硬约束 |
|---|---|---|---|
| 1 | **新建项目**：填项目名 → 选 PLC（逻辑类别）→ 选/摆放外围设备拓扑 | 生成项目实体 + **逻辑占位拓扑** | 不填型号、订货号、槽位、绝对地址；不要求先上传资料 |
| 2 | **项目内对话**：自然语言描述设备运行逻辑，或上传资料 | 解析回执、锁定资料、增量修改逻辑模型 | 会话绑定 `project_id`；上传资料为**可选补充**，不虚构条目 |
| 3 | **Canvas 渲染**：每个设备的执行单元、工站交互逻辑 | 三区域画布（上逻辑拓扑 / 中工艺逻辑 / 右变量） + 四视图投影 | 画布是**模型的可视化投影**，不是另一份数据 |
| 4 | **手动编辑**：增删改工站 / 执行件 / 连线 / 属性 | 画布同步回写**同一份**逻辑模型 | 所有写入口收敛到受控 patch；确认前零副作用 |
| 5 | **完全确认设备逻辑** | 冻结规格 vN（`spec_hash` + 完整快照 + 基线锁定） | 前置：拓扑定稿、`open_questions` 清零、等价性预检通过 |
| 6 | **一键导出 AF 架构 TIA 项目** | 工程包 + `fidelity_report` + evidence bundle；可选写入博途编译 | 1:1 可证明；编译零错误为终态验收 |

### 1.4 边界：做什么 / 不做什么

**做**：逻辑拓扑占位、设备逻辑建模、双向同步画布、业务语言编辑、规格冻结、AF 架构映射、等价性校验、工程包导出、Openness 回写编译、证据链留存。

**明确不做**：具体硬件组态（交 TIA 补全）、型号/订货号/槽位/绝对地址、在线调试/仿真/下载到 PLC、HMI（后置）、云 SaaS / 多租户、多人实时协同、自制编译器或全语言 IDE、纯聊天机器人式建议。

### 1.5 关键设计原则

1. **项目是一等公民**：对话、资料、拓扑、编辑、规格、产物、报告全部挂 `project_id`，可重开可回溯。
2. **单一事实源**：`CanvasSpec` 是唯一权威；画布、Mermaid、导出文件都是它的确定性投影。
3. **业务语言在前，AF 术语在后**：前端说「工站 / 执行件」，AF 的 Unit/EM/CM 收进工程视角面板。
4. **确认前零副作用**：沿用现有四个副作用计数器（`ops/disk_writes/writebacks/generations` 恒 0）与「确认必须由用户显式点击产生，不得代劳或超时自动推进」。
5. **可证明优先于看起来对**：任何「1:1」主张都必须附带机器报告。

## 2. 「1:1 还原」的可判定契约

### 2.1 三层含义

| 层 | 含义 | 判定方式 |
|---|---|---|
| 无丢失 | 画布每个对象在产物中有确定对应物 | 正向 coverage matrix = 100% |
| 无臆造 | 产物不出现画布之外的**逻辑** | 反向 orphan = 0（框架基线白名单除外） |
| 可证明 | 不靠人眼判断 | `fidelity_report.json` + `spec_hash` + 产物哈希 |

### 2.2 域边界：为什么是「逻辑语义 1:1」

TIA Openness 的硬限制使「对象逐字节 1:1」不可能也不可取（以下为一手/准一手证据）：

- 外部源只支持 `.awl/.scl/.db/.udt`，`GenerateBlocksFromSource()` 生成块；**SCL 是唯一可纯文本从头生成的语言**，LAD/FBD/GRAPH 无文本源，只能走「SimaticML XML 导出 → 改参 → 覆盖导入」的模板法。([导入指南](https://github.com/renanlido/tia-openness/blob/main/docs/guides/import-lad-fbd-scl-blocks.md))
- **导入时无原生参数指定 OB 编号**，按导入顺序算法分配；要精确控制须预创建空 OB 或用 Openness Scripter；西门子更推荐 Global Libraries 而非源文件。([Industrial Monitor Direct](https://industrialmonitordirect.com/blogs/knowledgebase/s7-1200-ob-number-assignment-during-tia-portal-source-import)，行业来源强度中等)
- SimaticML 导入：**缺失实例 DB 不自动创建**、无块编号则自动分配、导入后数据可能不一致**必须编译**、单文件根对象须同类、`ImportOptions.Override` 先删后建。（同上导入指南）
- V18 起软件单元支持 `NamespacePreset`、PLC 块支持 `Namespace`；V16 起 `IgnoreUnitAttribute` 可把块从 unit 导入到 non-unit composition。([SIOS V18 中文 Readme](https://support.industry.siemens.com/cs/attachments/109815199/TIAPortalOpeness_zhCN_zh-CHS.pdf)、[英文 Readme](https://support.industry.siemens.com/cs/attachments/109773802/TIAPortalOpenness_en-US.pdf))

**因此定义**：

- **纳入 1:1**：工站/执行单元/执行件层次、连线与交互、步序与转换条件、联锁、PackML 模式状态机、命名与命名空间、调用关系、变量引用、逻辑拓扑节点与逻辑连接。
- **不纳入 1:1**：物理组态（用户已划给 TIA）、OB 的物理编号分配、TIA 自动生成的实例 DB、编译中间对象、框架基线库块版本。

> 这与用户「具体完善的组态可以去 TIA 补全」完全自洽：1:1 的域天然是**逻辑层**。

### 2.3 框架基线白名单（D2 落地）

现有 `plc_engine/af/greenfield_delivery.py` 会自举一批**架构必需但不在画布上**的产物。不分栏的话，「多出来的块算不算臆造」永远说不清。故定义 `framework_baseline`：

| 基线条目 | 来源 | 锁定方式 |
|---|---|---|
| `01_AF_Standard_Library` LAF / LBC 自举标准库块 | `greenfield_delivery.py:38-51,119-175` | 固定版本 + 内容哈希 |
| DB720 / DB1900 冻结标准访问 DB | 同上 | 固定版本 + 哈希 |
| `FC_Compat_*`、`FC_IoMap_ReadWrite`（`90_Compat_Frozen_Boundary`） | 同上 | 固定版本 + 哈希 |
| OB1 / 文件夹 XML / `folders.json` | `tia_delivery.py:248-336` | 固定模板 + 哈希 |
| `manifest.json` / `audit/*` / `docs/architecture_spec.md` | 同上 | 结构模板 |

**判定规则**：产物中任一逻辑块，必须能回溯到某个 `spec` 对象 id；**否则必须命中 `framework_baseline` 且哈希匹配**；两者都不满足 → 判定 `orphan`，`fidelity_ok = false`。

### 2.4 `fidelity_report.json` 判定规则（D1 落地，核心新增能力）

三个量化指标：

```
coverage = 已成功映射且校验通过的 spec 对象数 / spec 对象总数     要求 = 1.0
orphan   = 逻辑块总数 - 可回溯到 spec 的块数 - 命中基线的块数     要求 = 0
drift    = (spec_hash 不一致) + (基线哈希不匹配) + (映射字段被改写) 要求 = 0

fidelity_ok = coverage == 1.0 && orphan == 0 && drift == 0
acceptance  = fidelity_ok && static_gates_ok && compile_error == 0 && reproducible
```

报告须包含：`spec_version` / `spec_hash` / `framework_baseline_version` + 各条目哈希 / `coverage_matrix`（逐对象 `source_id → 产物定位`）/ `orphan_blocks` / `drift_items` / `unmapped_spec_objects` / `product_hash` / `generated_at` / `verdict`。结构示例见附录 B。

> 现有 `af_verification_report.json` 与四层静态门禁（`tia_delivery.py:367-435`）查的是「AF 合规与 SCL 可编译」，**不查画布 ↔ 产物的等价性**。这是当前最大的能力缺口。

### 2.5 单一权威源 `CanvasSpec`（D4 落地）

在现有 `GreenfieldIR`（`plc_engine/af/greenfield_ir.py`）基础上扩展：

| 域 | 现有字段 | 需补充 |
|---|---|---|
| 项目 | `project`（name / tia_version） | `project_id`、创建时间、AF 档位标记 |
| 逻辑拓扑 | **无** | `hw_nodes[]`（id / kind=逻辑类型 / label / protocol 标签）、`hw_links[]`、`cm_mounts`、`var_bindings` —— 从 `session.custom_hw` 平行状态收编 |
| 工艺层 | `units / ems / cms / control_nodes` | 保持不变，增加 `business_label` 为前端主显示名 |
| 逻辑层 | `steps / jobs / modes / interlocks / edges / io_bindings` | 保持不变 |
| 资料 | `contract` 引用 | 上传回执 id、锁定状态、`source_id` |
| 规格 | `views / spec_meta`（含 `open_questions`） | `spec_hash` 覆盖上述**全部**域；`framework_baseline_version` |

**收编后废掉 `session.custom_hw` 平行状态**，否则 D4 不成立。

### 3.1 已实现能力（代码实证，比我 v1.0 报告的判断更多）

## 9. 验收体系与最小验收用例

### 9.1 三层验收

| 层 | 判定 | 产出 |
|---|---|---|
| L1 逻辑等价 | `fidelity_ok`（coverage=1.0 / orphan=0 / drift=0） | `fidelity_report.json` |
| L2 可编译 | `compile_error == 0` 且四层静态门禁通过（warning 单列不并入成功） | 结构化编译报告 |
| L3 可复现 | 同 `spec_hash` 两次生成产物哈希一致；服务重启可恢复 FROZEN vN | `reproducibility` 记录 + `.zap19` |

**最终验收** = L1 ∧ L2 ∧ L3。三者缺一不得宣称「1:1 完成」。

### 9.2 最小验收用例（端到端）

样例：**1 个工站（Unit1）+ 2 个执行单元（EM1 上料、EM2 输送）+ 3 个执行件（CM）+ 1 条工站间交互连线 + 1 个联锁 + PackML Production 模式**。

1. 新建项目：选 PLC 逻辑占位 + 3 类外围设备占位（**不上传 IO 表**，验证 D7）。
2. 对话输入自然语言描述设备运行逻辑 → canvas 渲染。
3. 手动：新增 1 个执行件、删除 1 条连线、修改 1 条工站交互、改 1 处步序条件（验证 D6 与双向同步）。
4. 确认设备逻辑 → 冻结 v1，检查 `spec_hash` 覆盖拓扑与全部编辑。
5. Action A 导出工程包 → 检查 `fidelity_report.json` 为 `fidelity_ok = true`、coverage 100%、orphan 0。
6. 负例：人为删除一个产物块 → `fidelity_ok = false` 且列出 `unmapped_spec_objects`；人为塞入无来源逻辑块 → orphan=1。
7. Action B 写入博途 V19 → 编译零错误 → 归档 `.zap19` + 编译报告。
8. 重跑步骤 4–5（不改任何输入）→ 产物哈希一致（L3）。
9. 服务重启 → 从 `specs/v1.json` 恢复画布，与确认时完全一致。

### 9.3 证据包（EvidenceBundle）

`specs/vN.json`、`ir_snapshot`、四视图导出、连线清单、`open_questions` 清零记录、静态门禁结果、`fidelity_report.json`、结构化编译报告、PCEC 账本、`baseline_manifest.json`、产物哈希、`.zap19` 归档。

### 13.1 问题与产品定位的变化

用户于 2026-11-06 16:16 指出：「项目不可能靠一次描述就能完整的出来，在调试过程中会有问题，这个时候需要更新程序。如果能通过该项目直接更改 TIA 内的程序，避免每次修改都需要重新载入一次项目。」

核查结论：**TIA Openness 支持，且本仓库已有大半零件，只是网关 Greenfield 链没有并线**。更重要的是，这条需求推翻了 v2.0 隐含的「一次描述 → 确认 → 一键导出」单次闭环假设 —— 产品定位须从「一次性生成器」升级为「**持续迭代的工程伴生工具**」：首次生成只是起点，调试期在同一份已打开的工程上反复增量修改才是常态。

**六个边界（必须写进设计约束）**：

1. **不是逐行改代码**：Openness 不提供直接修改已编译块内逻辑的方法，唯一稳定路径是「SCL 外部源生成块」或「SimaticML XML 覆盖导入」，**粒度是块** ([技术解析](http://www.gooderp.com.cn/h-nd-28.html)、[Openness 概述](https://bbs.plcjs.com/forum.php?mod=viewthread&tid=650511)，中文技术/社区来源，强度中等)。
2. **工程侧 ≠ 在线侧**：改的是 TIA 工程文件；生效到 PLC 仍需 TIA 下载动作，本项目不做（D12）。
3. **覆盖会丢信息**：`ImportOptions.Override` 先删后建；XML 往返对代码/接口无损但**不保留注释、任务属性、编译器提示**；只读/信息属性不导入；可能丢失实例特定属性（起始值）；缺失实例 DB 不自动创建；**导入后必须编译** ([IMD 检查清单](https://industrialmonitordirect.com/blogs/knowledgebase/tia-portal-openness-v18-exporting-and-importing-fcs)、[SIOS 英文 Readme](https://support.industry.siemens.com/cs/attachments/109773802/TIAPortalOpenness_en-US.pdf))。
4. **Attach 用户 UI 不稳**：`ProjectService.cs:630-632` 自注「Attaching to an existing UI Portal often fails with Openness security checks」故改 `preferAttach: false`；`README.md:184` 明确禁用 MCP open 的 preferAttach；[西门子中文论坛](https://wap.siemens.com.cn/club/bbs/post/1970455.html)有 V18 UI 模式 `GetProcesses()` 返回空/不可附着报告；另有 Openness 防火墙白名单（拒绝三次抛 `EngineeringSecurityException`）；[V21 还有 Dispose `GetProcesses()` 句柄会杀掉用户会话的坑](https://skillsmp.com/zh/creators/siemens/tia-portal-ai-extensions/openness-development-skills-session-and-project)。
5. **会话 / 文件锁冲突**：项目被另一进程或用户打开时可能抛 `EngineeringTargetInvocationException`（IMD 故障矩阵）；需约定「谁持有项目」并用 `ExclusiveAccess`。
6. **版本与能力硬约束**：V19 需匹配 V19 `Siemens.Engineering.dll`；F-block / Safety 被 CLI 明确拒绝（`README.md:63`）；OB 编号导入时按算法分配（§2.2）。

### 13.5 Action C 完整设计

**§4.8 的 D3 由「两动作」扩展为「三动作」**：Action A 导出工程包（可离线校验）／Action B 首次写入博途并编译／**Action C 调试期增量回写**（以 A 的 `fidelity_ok` 与已完成 B 为前提）。

**Action C 八步**：

1. **会话复用**：`SessionServer /open` 打开同一 `.ap19` 一次并保持（D9）；后续迭代不再 open、不再 create-project。
2. **规格差异**：`spec vN → vN+1`，复用 `begin_edit`（`greenfield_service.py:375-381`），产出 `changed_blocks[] / added[] / removed[]`。
3. **反向保护（新增）**：用 `tia.list_blocks` / `tia.export_block` 读 TIA 侧现有块，与上次生成物哈希比对；**不一致即阻止并提示，不覆盖**（D10）。
4. **差异清单显式确认**：前端列出将被覆盖/新增/删除的块与影响范围，用户显式点击（D11）；确认前零副作用计数器恒 0。
5. **写前备份**：快照 + 回滚钩子（`FastWriteback.cs:54-57`、`writeback_safety.py`）。
6. **块级覆盖**：仅对变更块执行 `GenerateBlocksFromSource(overwrite:true)` 或 `ImportBlock(xml, ImportOptions.Override)`；`ExclusiveAccess` 只覆盖写入段。
7. **编译 + 保存**：`compile-plc`（`error_count == 0`、warning 单列不并入成功）+ `save`；**不归档、不重载项目**。
8. **增量 fidelity + PCEC**：重算 coverage/orphan/drift（变更块全量 + 全量抽检），写 PCEC 账本，产出增量报告与 evidence bundle。

**会话归属与并发**：默认专用后台实例持有项目（D9）；若用户 UI 同时打开同一项目，提示关闭或转为只读观察；断线重连复用同一会话；启动预检 Openness 用户组 token（`ProjectService.cs:623-627`）与防火墙白名单。

**不在范围**：在线下载 / online / run-stop / compare-to-PLC、F-block 与 Safety 写入、全局库、UI 自动化（沿用 `README.md:53-68`）。

### 13.6 对 1:1 契约的扩展

`fidelity_report.json` 增加 `mode: "full" | "incremental"`、`base_spec_version`、`changed_source_ids[]`、`reverse_protection`，并新增**第 4 个指标**：

```
tia_side_drift = TIA 侧块与上次生成物哈希不一致的块数     要求 = 0

fidelity_ok = coverage==1.0 && orphan==0 && drift==0 && tia_side_drift==0
```

增量模式下 coverage/orphan/drift 对**变更块**须 100% 通过，并对全量做抽检；`tia_side_drift > 0` 时 Action C 在步骤 3 即被阻止。附录 B 的结构示例在增量模式下追加上述字段。
