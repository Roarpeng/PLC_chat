01 / PRODUCT THESIS

aiCoPlc 不需要替代 TIA Portal

让工艺专家定义设备应该如何工作，让工业编译器负责如何正确实现。
WHAT

工艺工程师

描述步骤、动作、反馈、联锁、超时、异常、复位和验收条件。

HOW

ProcessOS

将描述变成可执行契约，再映射到 AF/Nexeed 框架，生成与验证控制软件。

WHERE

原生工具链

TIA/Openness 完成真实工程、硬件上下文、编译与归档。现场验证和部署保留人工控制。

最应改变的产品语言：少说“生成一个 FB”，多说“建立一份夹紧工艺契约”。FB 是某个框架、某个 PLC 平台上的实现结果，不应该是工程师第一次描述需求时的核心认知。

示例：一个“夹紧”契约

EM · ClampStation / 夹紧单元

自动运行：在 Unit 允许自动、气压许可、门关闭且资源空闲时接收夹紧作业。命令气缸伸出，确认伸出位；保持 2 秒后缩回，确认缩回位，返回完成。

禁止动作：伸出和缩回命令不能同时成立。丢失全局许可时执行已定义的停机响应，不猜测安全动作。

异常：任一方向 3 秒未到位 → 锁存故障、撤销自动作业许可、等待人工处理。复位前需确认故障已消除，且设备处于允许复位的状态。

05 / FRAMEWORK TARGETS

AF 是强制目标架构，但不是用户交互语言

这里区分两个层次：工艺需求不直接依赖 AF 类名；一旦选择 Siemens AF 目标，所有可交付的逻辑必须满足 AF Profile 的类型规则、接口和调用约束。

Unit · AssemblyUnit
模式 / 状态 / 系统许可 / 故障汇总 / 与上层接口
↓ 标准 Unit–EM 接口
EM · ClampStation
Job / Sequence / CallEquipment / 报警 / ControlNodes

Sequence

步序、Guard、Time Budget

ControlNodes

工艺命令、状态与监控

CallEquipment

CM 调用与联锁仲裁
↓ 经已验证的 CM 接口
CM · ClampCylinder
批准的 LBC 或兼容 CM 模板：驱动命令、监测反馈、处理超时

六项不可让 AI 绕开的结构规则

  1. Unit 管理设备级模式和状态，EM 承载工艺功能，CM 执行和监控设备动作。
  2. Sequence 的生产动作经 ControlNodes/标准接口进入 CM，不绕开 CM 直接写物理输出。
  3. 传感器反馈和执行器调用顺序服从已锁定 AF 模板；不能仅凭代码名字推定兼容。
  4. 同一输出拥有明确写入者，互斥命令有确定仲裁顺序。
  5. 实例 DB、库块、UDT、命名、OB 调用和初始化来自已验证模板，不从自然语言凭空生成。
  6. 库版本、PLC 版本、工艺模型和代码映射一起锁定；库升级等同于工程变更。
现实版本边界：官方 AF Basic V2.2.2 提供 V20 工程，并要求 V20 或以上。若坚持 V19，必须先证明有合法、可复现、真实编译的 V19 框架基线；不能把 V20 官方工程宣称为 V19 兼容。后续 Nexeed 需自己的正式库、映射和工具链，不复用 Siemens AF 的 SCL 生成器冒充合规。
06 / UX

工程师实际看到什么？

左 · 工艺协商

对话不是“生成代码”。当工程师说“夹紧后送料”，系统识别不明确条件，提出少量必答问题。

中 · 工艺地图

以设备功能、步骤、条件、并行资源和异常分支展示逻辑，自动区分 Unit、EM 与 CM。

右 · 合同与证据

显示当前节点的条件、反馈、定时、联锁、错误处理、审批和行为测试结果。

一项变更的交互流程

01
描述：“增加气缸保持 2 秒，并且送料不能和夹紧冲突。”
02
解析：AI 提议工艺变更，显示涉及的 EM、资源、过渡条件和缺失信息。
03
预览：画布呈现新步序，同时给出合同差异（新增定时、互斥规则）。
04
验证：规则检查 + 场景模拟。如果发现冲突，返回最小失败轨迹，而不是只给红色报错。
05
审核：工程师确认行为契约和验证结果。确认的是可解释的工艺变化，不是几百行 SCL。
06
构建：锁定框架模板、生成、Openness 编译、归档、校验和下载。
07 / BROWNFIELD RETHINK

旧项目不是“代码转换”，而是“工艺考古 + 清洁重建”

旧工程侧 · 证据采集

  1. 以只读方式打开原件，并创建冻结的工程基线。
  2. 获取块、调用图、接口、交叉引用、标签和可访问的源代码。
  3. 识别设备、动作、状态机、报警、异常路径。
  4. 将每项推断关联到实际源块、行或调用边。
  5. 对未知和受保护模块给出“不确定/无法转换”。

新工程侧 · 规范化实现

  1. 形成工艺候选图，按信心水平分区。
  2. 工程师确认真正的工艺行为，而非接受所有旧写法。
  3. 生成新的 Process Contract。
  4. 使用批准的 AF Unit/EM/CM 模板重新生成。
  5. 能执行的情况下，对新旧版本做差分场景测试。
关键原则：不对旧工程做“AI 随手修复”。原件只读保全。不能证明行为等价的部分不能自动替换；旧项目不具备可重放工况时，不得声称“行为等价”。
08 / BUILD PIPELINE

两类产物，两个交付等级

产物 A · 工艺逻辑包

包含 Process Contract、AF 映射、SCL/SimaticML、接口契约、测试场景、哈希、报告。

特点：可不提供硬件货号，但不声称已经在用户现场的真实 PLC 上编译或验证。

产物 B · 原生 TIA 工程

依赖一个可用的 PLC 工程上下文：经批准的 CPU 模板，或者用户导入的真实 TIA 工程副本。由 Windows Worker 调用 Openness。

特点：可验证真实编译、归档、重开；与用户现场硬件组态是否一致需要单独核验。

原生工程编译状态机

SPEC_APPROVED → FRAMEWORK_PROFILE_LOCKED → BEHAVIOR_VERIFIED → SOURCE_GENERATED → PROJECT_COPY_OPENED → AF_LIBRARIES_RESOLVED → BLOCKS_IMPORTED → NATIVE_COMPILE_SUCCESS → SAVE_SUCCESS → ARCHIVE_HASHED → REOPEN_VERIFIED → DOWNLOAD_READY 任一失败 → FAILED + 诊断回执 + 可重试任务 禁止：测试未通过却发布；未经人审覆盖原工程；仅有源码包就显示“原生工程已完成”

构建工程安全：Windows Worker 与 Web/API 隔离；一次任务只操作一个沙箱工程副本；多任务通过队列串行或按隔离实例调度；固定依赖版本；生成可核验的证据清单。下载令牌绑定项目、构建任务、工件哈希和授权用户。

验证等级不能混为“测试成功”

10 / COMPETITIVE MOAT

我会押注四项真正难以复制的能力

01

Process Contract Compiler

将不严谨的自然语言转成确定、可版本化、可测试的工业工艺契约，并在框架层强制合规。

02

Counterexample-driven Interview

AI 不以“不确定但照做”处理疑问。模拟引擎发现反例后，回问工程师最少的关键问题，把工艺规格补完整。

03

Legacy Behavior Archaeology

旧程序逆向得到“带证据的工艺地图”，按真实来源、推断信心和不可解析边界区分；可做差分场景验证。

04

Build Evidence Passport

每个下载工件绑定需求、审批、框架版本、测试轨迹、编译诊断、归档 SHA256 和重开记录；无需相信 AI 的口头“已完成”。

附加方向：把成功的 EM/CM 工艺契约抽象为经验证可复用的参数化工艺单元。以后对话是“复用夹紧模块并更换保压时间”，而不是从零生成一个新的 FB。这将显著降低生成错误和重复成本。

12 / DELIVERY STRATEGY

不采用功能清单式开发：先突破最小真实闭环

P0 · 工程事实验证

选定实际可用的 TIA + AF 版本；取得合法工程模板与库；验证 Openness 导入、实例、编译、保存、归档、重开链路。版本不通，后续不扩大功能。

退出标准：真实 AF 示例包含 Unit + EM + CM + Sequence，并在指定版本真实编译及归档。

P1 · 工艺契约最小模型

实现命令、反馈、状态、Guard、超时、资源互锁、异常与版本化 Patch。实现离线模拟器及人工审核。LLM 只负责意图候选。

退出标准：首次完整「对话 → 契约 → 审核 → 行为验证 → AF 构建 → 下载」验收通过。

P3 · 工艺系统规模化

实现多个 EM、资源争用、并行/汇合、参数化模板、故障恢复、版本差异和复用工艺组件库。

退出标准：多模块测试与合法变更可重复编译；跨模块写冲突可被静态拒绝。

P4 · Brownfield 逆向重构

导入原始工程副本，建立调用图与证据链，输出待确认工艺地图，重建为 AF 契约并生成清洁工程。允许未知/保护块保持不可转换。

退出标准：真实旧工程能分类标注；可解释的改造在副本中成功编译并记录差异。

P5 · 工程扩展与现场协作

加入硬件绑定检查、PLCSIM/FAT 测试接入、审查权限与部署审批。仅在具备正式库、授权与真实工具链后建立 Nexeed 后端。

退出标准：不同验证等级、角色和审批责任有明确证据，不以“编译完成”冒充投运批准。
