### 1.4 `--real` 四个必填参数如何取值

`scripts/tia_delivery_chain_v2.py:55-60` 强制要求 `--cpu-type-id` / `--workspace-dir` / `--job-id`，`--output` 为可选但方案列为必填（证据留痕）。`--project-id` 默认 `prj_v2_real`，**必须与 job 的 `project_id` 一致**（否则四元组绑定与下载授权会不匹配）。

| 参数 | 取值 | 来源 / 注意 |
|---|---|---|
| `--workspace-dir` | `${G5_ABS}` = `C:/Users/.../plc_project/tmp_validate/v2_real_<TS>`（**必须绝对 Windows 路径**） | `execute_chain` 用 `Path(request.workspace_dir)` 派生 `tia_project/`、`archive/`、`reopen/`；CLI 的 cwd 是 exe 目录，相对路径会在错误位置创建工程 |
| `--job-id` | 先经 v2 API 创建 delivery job 得到（§3.3 阶段 A），写入 `${G5_JOB_ID}` | **关键陷阱**：`get_store()` 是进程内单例，`PLC_V2_DB_PATH` 未设置时默认 `:memory:`（`workspace_v2.py:124-125, 614-619`）→ 建 job 的进程与执行 `--real` 的进程看不到同一个 DB，`run_chain` 会抛 `ProjectNotFoundError`。必须设置 `PLC_V2_DB_PATH` 指向同一持久化文件，且两进程 cwd 一致 |
| `--cpu-type-id` | `6ES7511-1AK02-0AB0/V2.9` | 主理人 U-02 裁定，`evidence/v2/T01/cpu_selection.json`：`selection_status=selected_by_lead`、`verification_required=true`、`verified_create_with_item=false`、`approved=false`。`cpu_verification_v2.py:26` `LEAD_SELECTED_CPU` 与之硬一致；`:83-90` 传其它型号直接 fail-closed，绝不自动换型号 |
| `--output` | `${G5_EV_ABS}/chain_receipt.json` | `_emit()` 用 `Path(output).write_text`，父目录自动创建 |
| `--manifest-json`（强烈建议） | `${G5_ABS}/manifest.json` | 见下方「SCL 物化」；空 manifest 会让 Import 阶段成为空操作，无法证明 AC-01 第 5 步导入了真实生成物 |
| `--project-id` | `prj_g5_real` | 与阶段 A 建 job 的 `project_id` 完全一致 |

**SCL 物化（必须做，否则 Import 阶段必然失败）**：`TiaOpennessCliAdapter.import_blocks`（`tia_delivery_v2.py:225-243`）把 `manifest.import_order` 中的 `path` **原样**作为 `--scl` / `--xml` 传给 CLI，而 CLI 的 cwd 固定为 `bin/Release/net481/`。T04 的 `CompilerService.lower()` 产出的 path 是 `scl/UDT_DriverState.scl` 这类相对路径，磁盘上并不存在。因此执行前必须：
1. 用 `CompilerService(ir.af_profile).lower(ir)` 得到 manifest；
2. 把每个 `ArtifactFile.content` 写到 `${G5_ABS}/generated/<原 path>`；
3. 构造新 manifest，`files[].path`、`import_order`、`dependencies` 的键/值全部替换为**绝对路径**（`ArtifactManifest.validate_import_order()` 按 path 索引，替换后仍一致；`_role_of` 按文件名前缀判定，绝对路径不影响）；
4. `refresh_hash()` 后写 `${G5_ABS}/manifest.json` 供 `--manifest-json` 读取。

## 5. 失败、超时与进程崩溃处置

### 5.1 超时基线（如实记录，非统一 300s）

| 命令 | 超时 | 来源 |
|---|---|---|

| `import-xml` | 300s | `:238` |
| `compile-plc` | 900s | `:247` |
| `save-project` | 300s | `:251` |
| `archive-project` | 900s | `:257` |
| `retrieve` | 900s | `:262` |
| 整体上限（建议） | **3600s**（外层 `timeout 3600`） | 本方案 |

`openness_cli()` 用 `subprocess.run(timeout=timeout_s)`；`TimeoutExpired` 未被 wrapper 捕获，会冒泡到 `execute_chain` 的 `except Exception` → `TIA_UNAVAILABLE` fail-closed（`tia_delivery_v2.py:305-313` 等各阶段）。**但** `subprocess.run` 只 kill 直接子进程（CLI exe），CLI 以 `WithoutUserInterface` 拉起的 TIA Portal 进程树可能残留。

### 5.2 kill 策略（超时/挂起后，谨慎执行）

```bash
# 1) 只做只读确认，先不杀
tasklist /FI "IMAGENAME eq TiaOpenness.Server.exe"
tasklist /FI "IMAGENAME eq Siemens.Automation.Portal.exe"

# 2) 仅对「确认由本次链启动」的 PID 执行（不要杀 ALM 服务 / 用户已开的 TIA）
taskkill /PID <本次 CLI pid> /T /F
taskkill /PID <本次 Portal pid> /T /F
```

禁止：`taskkill /IM Siemens.Automation.Portal.exe /F` 这种全局按名杀（可能杀掉用户会话）；禁止杀 `almsrv64x` / `ALMPanelPlugin`。若无法区分 PID 归属，**保留进程并如实标注 `RECOVERY_REQUIRED`**，交主理人串行排期处理。

### 5.3 幂等与二次执行

- `idempotency_key = "g5-real-20261110-001"`（示例，实际带 TS）：`WorkspaceStore.insert_job` 按 key 去重返回既有 job（`workspace_v2.py:428-434`），`DeliveryCoordinator.start` 返回 `idempotent_hit=true`，**不会重复建 job / 重复导入**。
- 重跑前先读 `GET /api/v2/delivery-jobs/{job_id}`：若 `state == NATIVE_ARCHIVED` **禁止重跑**；若 `FAILED` / `RECOVERY_REQUIRED`，用 `DeliveryCoordinator.recover(job_id)` 出 `stage_cursor` 计划，**不盲目重发非幂等写入**。
- 二次执行必须使用**新的隔离目录时间戳**（`v2_real_<TS2>/`）与新的 `--output`，绝不覆盖首次证据。

### 5.4 失败证据保留

- 失败时把 `chain_stdout.txt`、`chain_receipt.json`、`T02/job_<id>_failed.json`、`T02/cpu_create_with_item_probe.json`、job events、隔离区 `run.log` 复制到 `evidence/v2/real/failed_<TS>/`。
- **保留隔离区 `tmp_validate/v2_real_<TS>/` 不删**（含已生成的 `.ap19` / `.zap19` 供复盘），24h 后由主理人书面决定是否清理；禁止通配删除。
- `FAILED` / `RECOVERY_REQUIRED` 时 API 不提供原生归档下载按钮（`projects_v2.py:344-374` + `get_job` 的 `native_artifact=None`）。
