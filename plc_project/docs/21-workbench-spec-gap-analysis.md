# 21 · 工作台规范差距分析与实施计划

日期:2026-10-25 · 依据:`docs/PLC_chat.html`(工艺驱动工程工作台实施规范 v1.0)对照当前 main(`cc057f6`)实况逐条核对(含代码检索验证,非凭文档推断)。

## 一、规范要义(一句话)

把产品从"对话式 PLC 工具"升级为"**工艺驱动的工程工作台**":工程师描述**设备应该怎么工作**(工艺需求卡),AI 对照现有工程产出**最小变更**,四层审查(工艺/逻辑/源码/验证)后走既有 PCEC 门禁执行——工程师管工艺意图,AI 管逻辑实现,系统管证据与验证。

## 二、差距总览(对照 §11 验收清单逐项核实)

### A. 已具备,验收项直接满足 ✅(规范写作时已基于我们最新代码)

| 验收项 | 现状证据 |
|---|---|
| 项目未加载时 AI 明确提示,不假装分析 | 空白画布问句引导(8361b82) |
| 基线变化 → 过期变更拒绝 | PCEC 基线门禁(锚定 original 副本),真机 E2E 验证过 expired 路径 |
| 未执行验证不显示通过;V3 未执行明示 | V0-V3 四级展示(确认弹窗+变更记录),pending≠pass |
| AI 不默认创建占位变量 | UserVar 捏造已杀(7a5f272),命名惯例(i_/o_/stat_)强制 |
| 写回走后端审批/备份/基线/PCEC;不绕过 | 确认门禁→PCEC 事务→fail-closed 全链;无 PLC 下载能力(产品边界明确) |

### B. 部分具备,需增强 ⚠️

| 规范要求 | 现状 | 缺口 |
|---|---|---|
| §03 工程上下文常驻(项目/CPU/TIA 版本/基线/解析覆盖) | 顶栏仅项目名+TIA V19+网关状态;基线指纹只在确认弹窗出现 | 缺工程概览头:CPU 型号、基线指纹、解析覆盖度、块/设备数、最近解析时间 |

### C. 完全缺失(P0 主体)❌(已代码检索确认零命中)

1. **项目入口与工作台上下文**(§03/Phase1):启动无"继续项目/导入工程/从工艺需求开始"选择;空白画布是唯一起点(虽有引导文案);
2. **四类任务快捷入口**(§04):理解工程/诊断问题/完善逻辑/重构——无任何任务型 UI(自然语言是唯一入口);
3. **工艺需求卡**(§05,P0 核心):intent_summary/preconditions/normal_sequence/exceptions/constraints/acceptance_criteria/open_questions 七字段、**来源三态标注**(工程证据/AI 推断/待确认)、**需求确认与变更批准分离**——全部不存在;
4. **后端需求对象**:`requirement` 在 pcec.py/路由零命中(§08 ProcessRequirement 概念契约未落地)。

### D. 缺失(P1/P2,规范也排后)❌

- §07 重构任务模式(行为保持约束、回归清单、影响展示)——与 AF P3 映射器(docs/18)天然衔接;
- §08 工艺语义双向追踪(点工艺步骤→块/变量;点变量→需求;未关联明示)。

## 三、实施计划(遵循规范 §12 执行约束:复用优先/最小改动/逐阶段/测试同步)

### Phase 0 · 盘点与基线(本报告即交付)✅
基线:后端 514 / 前端 100 测试全绿(cc057f6);服务运行正常;差距如上。

### Phase 1 · 项目入口与工程上下文(P0,1 个迭代)
- 启动态:无活跃项目时呈现「继续最近项目(列表)/ 导入工程 / 从工艺需求开始(→Phase2 需求卡)」三入口(复用 session_store 与 workspace meta,不新建状态源);
- 工程概览头(常驻):CPU 型号/TIA 版本/基线指纹(前 12 位)/解析覆盖(converted/parsed/interface_only)/块与设备数/最近解析时间——数据复用 job summary + workspace meta + PCEC baseline;
- 空态/加载/网关离线三态反馈。
**验收**:打开应用必先见项目选择;选中后上下文常驻可见。

### Phase 2 · 任务入口与工艺需求卡(P0,1-2 个迭代,可与 Phase1 并行)
- 顶栏四任务快捷入口(快捷方式≠独立后端,共享同一上下文);自由文本保留;
- **RequirementCard**:七字段 + 每条目来源三态(工程证据绿/AI 推断琥珀/待确认红);工程师可编辑;**确认按钮只标记工艺意图确认**,绝不触发 ops/写回;
- 后端:`ProcessRequirement` 最小对象(§08 字段裁剪)+ `/canvas/requirements` CRUD(风格同 session_store;存 PLC_WORK_DIR/requirements/);需求卡与 PCEC 事务经 `requirement_id` 弱关联(PCEC 增可选字段,兼容不破坏);
- LLM 生成需求卡:输入工艺描述+画布上下文→产出带来源标注的卡片;未知参数 → open_questions,不默认写值。
**验收**:需求确认≠批准(测试:确认后无任何 ops 产生);未知参数不上屏为已确认。

### Phase 3 · 四层变更审查(P0,1 个迭代,依赖 Phase2 契约)
- ChangeReviewDrawer(同一 change_id 驱动四 Tab):工艺差异(关联需求条目+验收条件)/逻辑差异(触及块·信号·HMI 绑定清单,点击→画布定位高亮)/源码差异(复用 SclDiffPreview+源码抽屉)/验证差异(复用 V0-V3+诊断);
- 证据点击定位:打通 对话/需求/差异 → 画布 selectBlock/focus(复用现有跳转机制,失败显因)。
**验收**:四层对应同一变更集合;定位失败显示原因。

### Phase 4 · 重构模式(P1)/ Phase 5 · 双向追踪(P1/P2)
按规范 §10 执行;Phase4 与 AF P3(存量映射器)合并设计,行为保持约束进 PCEC constraints 字段。

### 多 Agent 并行编排
Phase1(前端为主)与 Phase2(前端组件+state+后端 requirements API)文件域正交,可双线并行;Phase3 需前两者契约稳定后开。每阶段:契约先行 → 并行 → 全量测试 + 真实工程手动链路验证(导入→任务→需求卡→草案→审查→编译结果)。

### 测试义务(规范 §12.9)
无工程上下文提示(已有,补测)、需求确认不触发写回、审批门禁、证据定位失败反馈、V 状态真实显示(已有)、基线过期拒绝(已有)、回归全绿。
