01 · 核心判断

推荐方向：工程语义平台
PLC_chat 的长期壁垒不是更聪明的聊天模型，而是一个可追溯的 PLC 工程语义模型，以及围绕它建立的验证、变更、仿真和回滚机制。

仓库已经不是“聊天框 + 代码生成”这么简单。它把 TIA 工程导出、离线解析、统一中间表示（PLC-IR）、逻辑知识图谱、工程画布、HMI 结构与交互、Openness 写回和真实编译反馈连成了工作流。下一步不应只堆更多按钮或 Agent，而应提高整个工作流的可信度。

WHAT IT IS

工业 PLC 工程工作台

把已有工程读出来、解释清楚、展示依赖关系，并让工程师在受控条件下提出和验证修改。

WHAT IT SHOULD BECOME

可验证的工程变更系统

每个修改都附带来源证据、影响分析、验证结果、批准记录和可恢复的前后快照。

WHAT NOT TO CLAIM

不是自动安全认证器

编译成功不等于工艺正确，更不等于功能安全合规或可以直接下装生产 PLC。

最重要的问题不是“AI 能不能改”，而是“系统凭什么允许这次改动进入工程项目”。

02 · 当前项目究竟在做什么

从仓库中的 plc_project/agents/plc/tia/、gateway/app/、frontend/src/ 与 industrial/tia_openness_cli/ 看，项目已经形成多条工程能力，不只是概念文档。

能力层从代码 / 文档看到的内容我对价值的判断
工程接入支持导入 XML / 导出目录 / ZIP；完整 TIA 工程可通过 Windows Openness 导出 SimaticML。仅有孤立的 .apxx 二进制文件不足以独立打开。明确分离离线分析与依赖 TIA 的工程操作，避免把所有事情绑定在 Windows/TIA。
语义解析SimaticML 解析为 PLC-IR；IR 对访问变量、表达式、赋值、网络、块类型、GRAPH 步骤等有结构化表示。这是 AI 之外最有积累价值的底座。IR 可以被图谱、审计、转换、测试共同复用。
图谱与证据维护块调用、信号读写等关系；聊天检索可返回相关图谱边与 SCL 片段；覆盖报告记录未解析内容和跳过原因。能降低“模型凭经验猜项目”的风险，应该进一步升级为每个回答和变更的证据契约。
工程工作台React/TypeScript 前端包含全局关系图、画布、变量检查、SCL 面板、聊天、HMI 面板、导入和编译作业状态。把程序理解从文本问答变成可以导航、筛选和操作的工程界面。
修改与编译存在类型化画布操作、SCL 预检、工程师确认、写前备份、Openness 导入/生成、严格编译、错误归因以及自愈相关流程。已经开始走向真实研发工作流。最需要补强的是“变更前后语义是否保持预期”，而不是只检查能否编译。
验证资产含大量 SimaticML 夹具和 pytest / Vitest / C# 测试；最新提交说明新增问题回归测试，并报告 54 个 Vitest 测试通过。回归测试方向正确；但仓库测试通过、真实 Openness 集成通过、真实设备安全验收，是三个不同等级的证据。
范围边界：项目主要面向工程文件分析、可视化、生成/修改工程源内容和 TIA 编译验证。代码编译成功并不等于 PLC 实际行为已在真实机械设备上验证；仓库文档也明确描述了部分语言或对象仍是 best-effort / TODO，例如稀有 STL、可执行 GRAPH 语义和部分 HMI 还原能力。

03 · 我理解的端到端架构

建议用“数据面”和“控制面”两条链路理解：数据面负责工程知识和证据；控制面负责修改授权与真实 TIA 操作。二者必须有关联，但不能混成一个让 LLM 自由决定的流程。

核心工程数据流

01 · Import输入与版本固定归档、项目文件、SimaticML；记录工程版本和哈希。
02 · Parse构建工程语义结构、信号访问、网络、调用、HMI、硬件及未解析项。
03 · Understand证据化理解可引用到块、网络、原始节点；未知处明确标记。
04 · Change变更集与验证做最小修改，分析影响，生成可复现验证。
05 · Commit批准后写回备份、编译、回报、对照差异；失败关闭并允许恢复。

04 · 已经值得保护和继续投资的资产

ASSET A

PLC-IR，而不是把 XML 直接喂给 LLM

IR 已把表达式、变量访问、类型、赋值等建模为对象。应继续让它成为解析、关系图、SCL 生成、测试和差异比较的共同底座。

ASSET B

未解析项与覆盖率被显式记录

coverage.py 不只给“成功/失败”，还记录导出、解析、跳过、原因和 TODO。这种诚实的降级能力是工业级系统比演示型 AI 更重要的特性。

ASSET C

离线解析与 Windows Openness 分离

Linux / CI 可以进行 XML 分析与回归测试；真实 TIA 工程操作放在 Windows 侧车。避免为了 Openness 把所有服务做成一个不可控的巨进程。

ASSET D

写回护栏已经超越“直接覆盖文件”

写前备份、备份超限时 fail-closed、dry-run、哈希幂等、编译诊断和限时作业等，是下一步设计事务化变更的现成基础。

我不会推倒重来：优先复用现有 IR、KG、覆盖率、ChangeSet、Canvas、TIA CLI 和测试夹具。最优的突破方式是在现有资产上加一层统一的工程变更协议和验证证据，而不是另起一个全新 Agent 框架。

05 · 我看到的真实短板与风险

以下分成两类：第一类是从仓库结构和实现直接观察到的问题；第二类是若要进入真实工程流程必须解决的系统性风险。

仓库本身的治理问题

发现为什么重要建议
文档漂移
顶层 README 的目录说明把解析核心描述在 plc_engine/tia/，但当前核心实现实际主要在 agents/plc/tia/；前者基本只有包初始化文件。		新开发者或代码 Agent 会在错误位置加功能、重复实现或者误判模块边界。指定唯一权威路径；README 生成实际目录图；对外接口层保留兼容 facade，禁止重复实现。
双实现并存
同时存在 gateway/app/ 与 plc_gateway/，以及多个 CLI / tool 入口。		容易出现路由、配置、业务逻辑和文档在不同版本分叉。写清“当前入口 / 兼容层 / 已废弃”矩阵；把架构图与包清单加入自动检查。
Openness 命名与路径不一致
部分旧文档仍提到 tia_openness_mcp，当前代码目录则有 tia_openness_cli。		照着旧文档执行会得到错误命令和路径。文档加版本标记和最后验证日期；启动脚本、README、测试使用同一权威配置。
多种测试证据层级混合
部分安全测试使用 mock 替换真实 Openness 调用；仓库提交信息另有真实 TIA 验证描述。		单元测试只能证明被测逻辑；mock 不证明实际 TIA 版本、许可证、工程锁、写回兼容性都正常。把测试明确分为单元、离线夹具、Windows/TIA 集成、仿真行为、现场验收，并保留各自结果。

产品与技术上的系统性风险

高风险

“可编译”容易被误解为“行为正确”

严格编译可以验证语法、类型及一部分工程一致性，但不验证工艺意图、时序、状态机边界、传感器故障响应或设备实际动作。

高风险

逆向转换不能默认等价

LAD/FBD/STL/GRAPH 的所有结构并不都能被简单布尔公式表示。未知指令、保持语义、边沿、定时器状态、ENO、跳转与扫描周期影响都必须保留和报告。

中高风险

自然语言意图有歧义

2026-10-22 的最新提交修复了纯询问“当前功能块作用”可能误触发默认新增变量的问题。意图识别必须先分清解释、建议、修改和写回。

中高风险

“AI 自愈”可能把编译错误修成逻辑错误

如果让模型自由重写整块代码，即使编译通过，也可能改变保持位、复位优先级或执行时序。修复范围应被限制在错误及其可证明影响内。

06 · 突破性思路：给工程变更“携带证明”

我建议把差异化能力定义为 Proof-Carrying Engineering Change（带验证证据的工程变更，简称 PCEC）。不是仅仅生成一个代码文件，而是任何建议修改都带着“为什么、改哪里、影响谁、怎么验证、如何恢复”的完整凭证。

突破 1

从源代码视角到多层工程语义

同时维护源代码忠实层、控制语义层、工艺/设备关系层。三层互相关联但不能互相冒充；未知语义不能被“漂亮的重构代码”覆盖掉。

突破 2

从文本补丁到类型化变更事务

LLM 产出的是结构化意图和候选 ChangeSet；确定性引擎验证操作、前置条件与影响；提交必须针对明确版本基线。

突破 3

从编译检查到行为证据

编译只是一个门。还要有工艺不变量、故障场景、边界条件和仿真结果；对不能验证的点，明确显示“未验证”。

三层模型：每一层回答不同的问题

模型层核心问题数据示例不可做的事
1. 来源忠实层
Source-faithful Model		原始工程到底是什么？哪些部分被完整解析？原始 XML、UId、Part/Wire、语言、块接口、版本、文件哈希、未解析节点。不得悄悄丢掉不支持的元件或将不确定语义当作确定事实。
2. 控制语义层
Control Semantics		信号如何影响状态与输出？依赖关系是什么？PLC-IR、调用图、READS/WRITES、置位复位、定时器/边沿/步骤语义、变量作用域。不能把编译通过直接推导为工艺逻辑正确。
3. 工艺与验证层
Process & Verification		设备为什么这么动作？修改后仍满足哪些要求？动作状态机、I/O 含义、互锁、允许条件、故障模式、HMI 绑定、测试场景、验收不变量。不应让模型自行虚构工艺要求或把未经确认的推断作为事实。

让知识图谱从“关系展示”升级为“影响分析引擎”

当前已有 CALLS、READS、WRITES 等关系。建议按可追溯原则扩展：SOURCE_OF、BINDS_TO、REQUIRES、INHIBITS、TESTS、CHANGED_BY、SAFETY_BOUNDARY。例如修改一个 DB 字段时，系统不只找交叉引用，还能列出：哪些 FB 读取它、哪些 HMI 控件绑定它、哪些测试依赖它、哪些告警/安全检查可能受影响。

真正的创新组合：确定性解析与校验负责“边界可信”；LLM 负责“语义解释、候选方案与测试建议”；TIA 编译器负责“工程编译证据”；仿真/测试负责“行为证据”；工程师负责“最终授权”。没有某项证据，就不允许界面把状态渲染成已验证。

07 · 建议的新核心：工程变更事务协议

建议把现有 Canvas Ops、PlcChangeSet、预检、备份、编译作业、自愈补丁统一到一个显式事务对象上。这个对象应当在 UI、API、后端执行器和审计报告中共用，而不是每条工作流各自维护状态。

{
  "change_id": "chg-...",
  "project_baseline": {
    "project_hash": "sha256:...",
    "tia_version": "V19",
    "parser_version": "..."
  },
  "intent": { "kind": "modify", "request": "...", "confirmed": true },
  "ops": [ { "op": "add_variable", "target": "MainDB", "...": "..." } ],
  "preconditions": [ "目标块存在", "基线哈希未变化", "非 F 程序写入路径" ],
  "impact": { "blocks": [], "signals": [], "hmi_bindings": [], "tests": [] },
  "verification": { "static": "pending", "simulation": "pending", "tia_compile": "pending" },
  "approval": { "reviewer": null, "approved_scope": null },
  "rollback": { "backup_hash": null, "restore_verified": false },
  "status": "proposed"
}

推荐状态机：失败不是成功，未知也不是成功

PROPOSED提出意图问答和修改是不同类别；不确定时先追问，不生成默认操作。
ANALYZED分析影响锁定项目基线、依赖范围、证据覆盖和潜在冲突。
VALIDATED验证候选静态预检、语义约束、场景仿真与真实 TIA 编译。
APPROVED人工确认批准某个具体差异和目标工程，不是笼统批准“让 AI 改”。
APPLIED落地并留账写回、编译、生成报告；失败则回滚或保留明确的未完成状态。

一个修改的“证据包”应包含

变更证据修改前后 IR 差异、原始源位置、生成补丁、项目版本与哈希。
影响证据受影响块、变量、调用链、HMI 绑定、相关 I/O 与安全边界。
验证证据静态审查、覆盖率变化、测试场景结果、TIA 版本与编译诊断。
审批 / 回滚证据批准者、批准范围、时间、备份位置、备份哈希和恢复测试结果。

关键细节：当目标工程基线已经变化，事务应因“过期”自动拒绝，而不是把旧补丁应用到新版工程。写回与编译也应保持同一个 Change ID 和相关日志 ID，以支持事后复盘。

08 · 工业安全边界：哪些自动化必须被禁止

必须说清楚：在普通 DB 中添加一个名为 EmergencyStop 的 BOOL，或者让 AI“补上急停逻辑”，绝不等同于构建了合规的急停功能。功能安全取决于硬件、F-CPU / F 程序、风险评估、验证流程和现场实现；AI 不能通过命名或编译结果为其背书。
动作级别默认权限建议必须有的门禁
L0 只读
导入、分析、解释、覆盖报告		可自动执行路径白名单、文件大小 / 类型约束、证据引用、不支持项显式披露。
L1 草稿
画布草稿、IR 变更候选、生成代码预览		可自动提出，不可静默应用明确标记 draft，显示差异与影响范围；修改不得改变原始工程。
L2 工程文件写回
导入外部源、改动 TIA 工程并编译		显式人工审批基线检查、备份成功、F 程序保护、目标工程隔离、超时可控、严格编译、结果记录与恢复手段。
L3 下载 / 在线控制
下载至 PLC、在线改值、触发设备动作		与当前 AI 自动写回链路彻底隔离；默认禁止独立权限系统、现场授权、变更窗口、LOTO / 安全流程、工程师双重确认与设备级联锁。

对“自愈”设硬边界

  • 只修被诊断覆盖的局部问题。 编译器报出某行类型不匹配，不应因此自由重构整个 FB 的控制逻辑。
  • 修复前后都跑相同的不变量和回归场景。 如果缺少行为测试，界面必须显示“语法修复完成，行为尚未验证”。
  • 任何安全相关对象默认只读。 F-块、F-标签、安全相关硬件和边界信息不允许常规生成器自动改写；漏检也不能等同于安全对象不存在。
  • 未知结构必须保留。 不支持的指令、GRAPH 或保护块应以原始内容和可见告警保留，不得悄悄删除或虚构行为。
  • 超时必须真正结束执行。 现有编译作业对“线程超时但 Openness 仍卡住”的风险已有说明；一次性 CLI 的进程树隔离应保留，远程 Worker 的取消边界必须继续清晰暴露。

09 · 落地路线：不推倒重来，先补“可信闭环”

建议按能逐步验收的能力来推进。先稳定边界与证据，再增加更聪明的模型；不要一开始就引入更复杂的多智能体编排。

PHASE 0

梳理唯一权威入口

目标：让开发者和代码 Agent 清楚哪里是正式实现，哪里是兼容入口，哪里是历史文档。

修正文档路径确定唯一 Gateway确定 TIA CLI / Worker 边界
  • 列出模块 owner、入口、被调用方向和废弃候选。
  • 统一 README、devctl、services.toml、路由和 Openness 命令路径。
  • 新增“架构文档与目录自动对照”检查，减少持续漂移。
PHASE 1

给现有 IR / 图谱加来源与可信等级

目标：所有展示的结论都能回到原始工程；所有未支持项都不会被伪装成完整理解。

Source UIDproject hashparser versioncoverage contract
  • 每个 IR 节点记录源文件、块名、网络 / 元件 UID、原始片段哈希、解析器版本。
  • 每个块有状态：完整解析、部分解析、仅接口、受保护、未知；状态不能只靠一个布尔值表示。
  • 统一覆盖率报告、对话引用和图谱中的节点 ID；无来源证据的回答标为推断。
PHASE 2

把改动统一成 PCEC 变更事务

目标：让聊天、画布、优化提案、自愈修复最终都产出同一种可审计对象。

Change ID基线版本影响范围审批与回滚
  • 把现有 ops 与 PlcChangeSet 映射到统一 schema，包含前置条件、目标、差异和失败状态。
  • 增加 read-only / draft / writeback 权限级别；提问类输入永远不能隐式触发修改。
  • 写回前强制进行版本基线比对、备份、范围检查；写回后保存完整审计包。
PHASE 3

从“编译验证”升级到“行为验证”

目标：至少对关键工艺约束证明修改没有破坏已知行为；区分无法验证和验证失败。

测试不变量故障场景HMI 绑定一致性仿真 / PLCSIM
  • 先为一个真实代表项目构建用例：启动/停止、互锁、复位优先级、定时器、传感器断线/粘连、HMI 绑定与告警。
  • 测试可由 AI 提议，但不变量需由工程师确认后成为验收基准。
  • 有条件时让同一测试在离线 IR 模型和 PLCSIM Advanced / 真实测试台复用；明确两种运行时的差异。
PHASE 4

将“现场知识”沉淀为跨项目能力

目标：把工程理解变成团队可以复用的故障定位和风险识别资产。

跨项目模式变更影响查询工程报告经验反馈
  • 利用历史故障、变更结果和验证记录，建立“症状 → 相关信号/块 → 可能原因 → 检查步骤”的证据型诊断。
  • 比较不同设备项目的相似控制结构，给出差异和迁移风险，不直接复制未经审查的逻辑。
  • 持续将未解析 Part、编译失败、自愈失败和人工驳回反馈到解析器/测试优先级。
最值得先做的下一项具体工作：不要先增加新 Agent。建立一份能自动产出的 Project Manifest + Coverage Report + PCEC Change Report，让任意工程和任意变更都有统一的身份、基线、证据、风险、验证与回滚记录。这会先把已有功能真正粘合成一个系统。

10 · 如何判断改进真的有效

不要只用“模型回答更像专家”或“页面更完整”来验收。用工程结果衡量。

指标建议的验收口径为何重要
解析覆盖率每个输入块都落入已定义状态；导出/解析/跳过数量能够对账；每个未解析 Part 有明确名称与原因。杜绝“只解析了大部分，却报告分析完成”的错觉。
证据可追溯率工程理解类回答与变更理由能够回到具体块/网络/源片段；无引用事实明确标记为推断。让工程师可以复核 AI 的说法。
行为回归通过率被修改区域和其影响邻域的关键不变量、边界场景通过；未运行的场景显示为未验证而非通过。编译仅验证工程可构建，不证明工艺不变。
写回完整性写前备份成功率、基线冲突拒绝率、严格编译结果、失败回滚演练结果都可统计。目标是可恢复，而不是假定每次写入都成功。
意图误触发率问答 / 解释 / 总结任务导致零修改操作；模糊意图优先追问；提交动作都有明确审核与日志。最近真实回归问题表明这是必须单独衡量的工业 UX 安全属性。
跨环境复现性离线夹具在 CI 稳定通过；Windows/TIA 集成测试注明 TIA 版本、许可证、样例工程与结果。可区分算法回归、平台依赖问题和真实工程差异。

“已验证”需要拆成不同等级

V0

结构已解析

确认源文件可读取，并记录支持率与未解析内容。

V1

静态校验通过

接口、引用、规则和局部不变量通过。

V2

TIA 编译通过

指定版本、指定工程副本中的编译器给出明确结果。

V3

行为验证通过

指定测试场景 / 仿真 / 测试台满足已批准的要求。

建议 UI 不显示一个笼统的绿色“成功”，而显示分级验证状态与证据链接。例如“V2 TIA 编译通过；V3 尚未运行”。
