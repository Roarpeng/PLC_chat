01 / PRODUCT INTENT

先统一产品目标

PLC_chat 不应以“AI 能生成多少代码”作为核心目标，而应降低工程师理解、完善和重构 PLC 工程的成本。工程师描述设备应怎样工作；AI 研究现有程序并提出实现；工程师审核后，系统执行允许范围内的工程变更与验证。

⌕

理解工程

说明设备工艺、程序结构、信号关系、动作条件和调用路径。结论必须能追溯到程序块、网络、变量或工程资料。

⇄

完善与重构

从工艺需求出发分析差距，提出最小变更。重构必须说明行为约束、影响范围与回归验证方案。

✓

验证结果

区分结构、静态、TIA 编译和行为验证。没有执行的检查不能标记为通过；编译通过不等于设备行为正确。

产品原则：工程师负责工艺意图、设备约束和最终决策；AI 负责把已确认的意图转化为可追溯、可审查、可验证的控制逻辑。不要要求工程师先决定 FB、变量名或 SCL 写法。

04 / USER FLOWS

四种任务模式，共享同一份工程上下文

快捷任务用于减少表达成本。自然语言输入继续保留，不能把用户限制在固定表单或固定指令。

TASK 01

理解工程

⌕
“这个设备的自动循环是怎么运行的？”生成工艺主线、启动条件、动作顺序、停止/复位与相关程序证据。
  • 先确认当前工程和解析覆盖度。
  • 用白话解释；术语可点击查看原始变量、网络或代码。
  • 明确说明未知、未解析或证据不足的部分。
TASK 02

诊断问题

⌕
“气缸没有伸出，但 PLC 已经发出动作命令。”输出候选原因、证据、排查顺序和需要读取的现场信号。
  • 从命令位向前追踪允许条件、模式、互锁、报警和状态条件。
  • 按证据强弱排序假设，不把推测写成根因。
  • 区分静态代码分析与真机实时信号诊断。
TASK 03

完善工艺逻辑

⇄
“夹紧不到位不能启动加工；超时要报警。”先形成需求卡，再对照现有工程，最后提出最小变更。
  • 提取前置条件、正常序列、异常分支、复位和验收条件。
  • 检查现有逻辑是否已经满足需求，避免重复添加。
  • 有关键歧义时只追问真正影响实现的问题。
TASK 04

重构程序

⤨
“把重复的夹紧逻辑抽成公共 FB，但行为不变。”展示重构范围、行为约束、调用影响、代码差异与回归计划。
  • 默认保持外部行为、接口语义和既有安全约束不变。
  • 先分析依赖，再生成重构草案。
  • 验证不充分时明确标注风险和未覆盖项。
交互规范：任务入口是快捷方式，不是不同的 AI 后端或独立上下文。所有任务都使用相同项目基线、解析状态、变量引用、历史意图和变更事务。
05 / PROCESS INTENT CARD

先确认工艺意图，再生成程序修改

这是 P0 的关键交互。AI 不应把一句口头工艺要求直接转成未经审查的写回操作。先生成工程师能理解的结构化需求卡，再做工程差距分析和修改草案。

工艺需求草案 · 示例

待工程师确认
01 / 前置条件

工件到位、自动模式有效，且项目定义的安全许可成立。

02 / 正常序列

发出夹紧命令 → 等待夹紧到位 → 允许加工。

03 / 异常分支

夹紧超时 → 报警 → 禁止加工；复位条件由工艺需求定义。

04 / 验收条件

未夹紧时所有相关加工启动路径均被阻断；超时时按要求报警；正常夹紧后流程可继续。

参数说明：超时时间必须来源于工程已有参数、工艺文件或工程师确认。本规范不指定实际设备时间值，也不允许 AI 将示例数值直接写入生产工程。
需求来源与置信状态每项都可标记
工程证据已从工程或文件确认，显示来源。
AI 推断推测或建议，不能伪装成已确认要求。
待工程师确认缺失的工艺参数、异常处理或边界条件。

需求卡字段契约

字段内容交互要求
intent_summary一句话说明用户希望设备实现什么。允许工程师直接编辑。
preconditions前置条件、模式和已有互锁。标明来源：工程证据 / 用户输入 / AI 推断。
normal_sequence动作顺序与状态转移。可按步骤检查、排序和修订。
exceptions超时、传感器矛盾、取消、复位等异常分支。未知项显示待确认，不自动编造设备行为。
constraints必须保留的接口、命名、动作和安全约束。为修改计划生成不可静默违反的约束。
acceptance_criteria如何判断工艺要求已实现。每条标准尽量能关联静态检查或测试场景。
open_questions对实现有实质影响的未知信息。优先一次问一个关键问题；允许在不影响安全的前提下继续做只读分析。
实施规则：需求卡确认只表示“工艺意图已确认”，不等于批准修改或批准写回。两种确认必须分开。
06 / CHANGE REVIEW

变更审查：同时看工艺、逻辑、代码与验证

工程师需要理解变更产生的设备行为，而不只是阅读代码 diff。所有视图应由同一份 change set 生成，并共享选中对象和定位信息。

01

工艺差异

新增或改变了什么设备行为？哪些异常流程得到处理？原有工艺约束是否保留？

显示关联的需求条目和验收条件。

02

逻辑差异

哪些条件、状态、动作、调用关系、变量、HMI 绑定被新增、修改或删除？

点击任意项，高亮画布中的对应块或信号。

03

源码差异

展示修改前后 SCL / SimaticML 或适用的逻辑表示。显示变更区块、命名和接口变化。

保留原始工程源、转换结果和解析限制等证据。

04

验证差异

展示结构解析、静态预检、TIA 编译和行为验证的独立状态、日志、错误归因及覆盖范围。

状态未知、跳过或未执行时，不能显示为通过。

变更状态与权限边界

01

草案

生成变更计划和候选 ops；尚未触碰 TIA 工程。允许继续编辑、放弃或重新生成。

Draft
02

分析与预检

计算触及块、变量、HMI 和调用路径；检查前置条件、项目基线与静态规则。

Analyze
03

工程师审查与批准

清楚展示变更清单、风险、基线指纹、备份方式和验证计划。批准范围必须与实际执行范围一致。

Approval
04

执行已有写回/编译流程

复用后端守卫、备份、Openness 和 PCEC。基线改变时必须 fail-closed，拒绝过期变更。

Writeback
05

呈现真实验证结果

成功时显示证据；失败时定位错误并可提出新的修复草案。修复仍需遵守既有安全和审批边界。

Evidence
安全边界：不在本次功能中增加 PLC 下载到 CPU 的能力。仓库现有说明明确产品支持回写博图和编译校验，不提供 PLC 下载。任何未来下载功能都需要单独的需求、安全审查和授权设计。AI 不得绕过用户审批直接回写、改变项目基线或执行现场动作。
07 / REFACTOR WORKFLOW

重构必须有明确的行为约束

“优化程序”是一个风险很高的模糊请求。系统应先明确优化目标，再分析影响，并将重构范围和行为保持要求纳入变更事务。

重构目标系统应检查必须展示
消除重复逻辑重复网络是否真正等价；实例状态、定时器、边沿和保持行为是否相同。重复候选、抽取后接口、实例数据差异与回归场景。
拆分复杂功能块输入/输出接口、静态状态、调用顺序和数据依赖。拆分边界、调用图变化、接口迁移清单。
改善命名与结构所有读写引用、HMI 标签、外部接口和跨块依赖。重命名映射、受影响项、原引用是否完整更新。
改善执行顺序或状态机周期执行语义、扫描顺序、状态保持、超时、复位和异常路径。行为变化声明、原/新状态转移对比、未验证风险。
性能或可维护性优化现有基准、真实瓶颈、可测量的目标。优化前后指标。没有基准时先提出测量，不声称性能提升。
默认约束：重构默认要求“外部工艺行为和接口语义不变”。若系统判断必须改变行为，必须把它作为显式工艺变更单独列出，不能藏在重构操作中。

重构任务的最低输出

  • 重构目的和范围。
  • 基线行为与必须保留的约束。
  • 受影响的块、接口、变量、HMI 绑定和调用关系。
  • 修改前后逻辑与源码差异。
  • 回归测试清单及覆盖度。
  • 已验证内容、未验证内容和剩余风险。
08 / PROCESS SEMANTICS

建立最小工艺语义关联，不要另造一套 PLC-IR

工艺步骤与 PLC 代码是两种不同的描述。要让 AI 真正理解工程，需要把“设备应该如何工作”关联到“现有 PLC 如何实现”。但这一层必须复用现有 PLC-IR、知识图谱和画布模型，避免多套事实源冲突。

A

工艺语义层

工艺步骤、前置条件、动作、互锁、异常分支、复位规则和验收条件。

Intent
B

现有 PLC 语义模型

PLC-IR、块、网络、变量、表达式、调用图、HMI 绑定与来源位置。

Implementation
C

实现与验证证据

源工程、SCL/SimaticML、编译日志、静态检查、行为测试及验证覆盖度。

Evidence

从工艺到代码

用户点选某个工艺步骤，即可看到对应的块、网络和变量。发现逻辑缺口时，系统能列出证据和受影响范围。

从代码到工艺

用户选中某变量或网络，可以查看它服务于哪些工艺要求。没有建立关联时明确显示“尚未关联”，不能让模型编造关系。

10 / DELIVERY ROADMAP

按阶段实施，每一阶段都能单独验收

建议先解决体验主线和工艺需求表达，再补充更深的工艺语义追踪。避免一次性重写前端、Agent 和后端。

PHASE 0

仓库盘点与基线验证 必做

检查当前分支、README、AGENTS.md、组件树、API 契约和测试；启动前后端；运行已有测试；记录基线失败项和截图/主要 UI 状态。

交付：简短盘点记录、确认的复用组件、测试基线。不要在此阶段做大规模重构。

PHASE 1

项目入口与工作台上下文 P0

在进入空白画布前提供“继续项目 / 导入工程 / 从工艺需求开始”；选中项目后展示工程概览、解析状态、设备/块数量和当前基线状态。保留现有历史会话和导入功能。

交付：可操作的项目入口、上下文明确的工作台、加载/空状态/错误状态。

PHASE 2

任务入口与工艺需求卡 P0

加入理解工程、诊断问题、完善工艺逻辑、重构程序四种任务入口；自然语言仍可直接输入。工艺变更先生成需求卡，显示来源、前置条件、正常序列、异常分支、约束、验收标准和待确认问题。

交付：需求卡状态流、编辑/确认操作、需求确认与变更批准分离。

PHASE 3

影响分析与四层变更审查 P0

在现有变更流程上显示工艺差异、逻辑差异、源码差异和验证差异；将证据链接到真实画布对象。复用 PCEC 状态机、基线门禁、变更记录和编译抽屉。

交付：可审查的修改草案、影响对象清单、验证状态和失败诊断。

PHASE 4

重构任务与行为保持验证 P1

支持“保持行为不变”等约束；显示调用影响、接口变化、回归测试清单和验证覆盖度。先做分析和草案，避免直接自动重写。

交付：重构计划、风险边界、前后对比和真实测试结果。

PHASE 5

工艺语义与 PLC-IR 双向追踪 P1/P2

在现有工程模型之上建立最小工艺要求对象，关联工艺步骤、块、变量与验证证据；通过真实案例验证映射准确度后再扩展知识图谱。

交付：需求到实现、实现到工艺的双向导航，未映射项可见且不伪造关系。

11 / ACCEPTANCE CRITERIA

验收标准：可观察、可测试、不可模糊

每个验收项都应有对应的自动化测试或可复现的手动步骤。以下清单可以作为 Agent 的完成门槛。

产品与交互

  • 打开应用时，工程师能继续最近项目或直接导入工程；不会无提示地落入没有上下文的画布。
  • 项目未加载时，AI 会明确提示当前没有工程上下文，不会假装分析真实 PLC 逻辑。
  • 四类任务入口都有清晰说明，并且仍可使用自由文本输入。
  • 工艺需求卡能区分工程证据、用户输入、AI 推断和待确认内容。
  • 需求确认不会自动等价为批准代码修改或批准回写。
  • 点击变量、逻辑块或工艺步骤，可以定位相应工程对象；定位失败时显示原因。
  • 变更审查同时展示工艺、逻辑、源码、验证四类信息，并且都对应同一个变更集合。
  • 窄屏、加载中、解析失败、网关离线、无变更和编译失败状态都有清楚反馈。

工程正确性与安全边界

  • 每条关键结论尽可能链接到真实工程证据；无证据的推断有明确标识。
  • 写回继续使用现有后端权限、审批、备份、基线检查与 PCEC 流程。
  • 工程基线发生变化时，过期变更不能被应用。
  • 任何失败或未执行的验证都不能显示为通过；V3 未执行时明确显示未验证。
  • AI 不能默认创建占位变量来掩盖未知信号，也不能静默改变接口或安全相关行为。
  • 不引入绕过人工批准的自动写回或 PLC 下载路径。
  • 重构任务默认保留外部工艺行为；行为改变必须明示并得到单独确认。

测试与交付证据

  • 前端单元测试通过；失败项逐个分类，不能用跳过测试宣称成功。
  • 后端单元测试通过，或清楚列出与本次变更无关的基线失败及证据。
  • 新增测试覆盖需求状态、批准分离、证据定位、变更摘要和验证状态显示。
  • 手动验证至少覆盖导入工程 → 选择任务 → 生成需求卡 → 生成草案 → 审查 → 编译结果呈现。
  • 若没有可用的 TIA V19 / Openness 环境，明确说明未完成真实编译验证，不得声称真机闭环已验证。
  • 提交变更清单、测试命令及真实输出、遗留问题、截图或操作记录。

12 / AGENT WORK ORDER

可以直接交给开发 Agent 的执行指令

将以下内容作为本规范的执行约束。Agent 应边检查、边实施、边测试；遇到复杂任务时分小步提交可审查结果，不要一次性生成大量未经验证的改动。

任务：依据《PLC_chat｜工艺驱动工程工作台：交互与开发实施规范》完善仓库。目标是让工程师专注工艺，AI 理解现有 PLC 工程并完善/重构控制逻辑，系统提供可追溯证据与验证闭环。

执行要求：
1. 先检查当前分支、AGENTS.md、README、前端组件、后端 API 契约、PCEC 和相关测试。确认当前实现与本规范的差距。不要仅凭文档推断代码已实现。
2. 先运行现有前后端测试并记录真实基线。不得把未执行的测试写成通过；遇到既有失败，保存命令、关键日志与归因。
3. 遵循“复用优先、最小改动、逐阶段交付”。不要重写整个 App，不要创建与现有组件/PLC-IR/PCEC 重复的平行系统。若已有能力满足要求，优先增加测试和修复实际缺口。
4. 按 Phase 1 → Phase 2 → Phase 3 实施 P0。每个阶段结束时运行相关测试并总结：改动文件、行为变化、测试命令与真实结果、未完成项。
5. 首先实现：项目入口/上下文、四类任务快捷入口、工艺需求卡、需求确认与变更批准分离、工艺/逻辑/源码/验证四层审查。不得只做静态 UI；交互应接入真实 state/API，或清楚标注尚未接通的能力。
6. 需求卡必须标注证据来源、AI 推断和待确认项。未知参数不得默认写入 PLC；关键不确定项要请求工程师确认。只读分析可以在不确定时继续，并说明边界。
7. 写回必须继续走现有后端 PCEC / 基线门禁 / 审批 / 备份 / 编译路径。不要增加未经批准的自动写回或 PLC 下载功能。基线过期时必须拒绝执行。
8. 验证状态必须区分结构解析、静态预检、TIA 编译和行为验证。未知、跳过、未执行不能显示为通过。没有真实 TIA 环境时，不得宣称真实 TIA 编译或设备行为已验证。
9. 同步补充单元测试。至少测试：无工程上下文提示、需求确认不触发写回、变更审批门禁、证据定位失败反馈、验证状态的真实显示、基线过期拒绝与既有功能回归。
10. 不做无关格式化或大范围重命名。不要删除历史功能和测试。避免前后端 API 契约漂移；新增字段要有兼容策略。
11. 在最终报告中明确列出：完成项、修改文件、关键设计决策、自动化测试真实结果、手动验证结果、未完成项和风险。将“已实现”“已测试”“真实工业环境已验证”作为三种不同状态报告。

完成标准：以本规范第 11 节验收清单为准；若某项受环境限制无法完成，交付最好的可验证部分，并明确说明阻塞原因与下一步。
已复制
执行顺序建议：不要先建设复杂的工艺知识图谱。先把“项目上下文 → 工艺需求 → 变更审查 → 验证结果”这条路径做顺畅，并通过现有真实 PLC 工程做端到端验证，再决定工艺语义层需要保存哪些字段。
