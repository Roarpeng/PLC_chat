# 20 · 对话历史压缩策略(调研结论与实现)

日期:2026-10-25 · 触发:指代性指令(「按步骤全部修改」)需要对话历史才能解析;用户要求调研压缩方式与压缩时机。

## 结论先行

1. **存储层永不压缩**:localStorage 与服务端会话账本是事实源(复制/回看/再展开都依赖全文),存储廉价,有损压缩只会丢信息——不存在"存一段时间再压"的需求。
2. **压缩只发生在"构建 LLM 上下文"的时刻**,每次请求即时计算:无定时器、无状态机,**不存在压缩时机问题**。
3. **方法:分级保真规则压缩(零额外 LLM 调用)**,而非全文塞入、也非 LLM 摘要。

## 备选方案对比

| 方案 | 做法 | 优点 | 否决/保留理由 |
|---|---|---|---|
| 全文塞入(截断到 N 条) | 最近 6 条 × 各 200 字 | 最简单 | 语义丢失:步骤清单(指代目标)恰在长助手消息里,一刀切截断会砍掉 |
| **分级保真(已采用)** | 最后一条助手消息近乎全文(≤1200 字,剥 markdown/脚注);其余消息压到首句+关键令牌(≤100 字);>6 轮丢弃;总预算 ≤2400 字 | 零成本零延迟零故障点;指代目标保真;DeepSeek 前缀缓存仍命中(骨架在前) | — |
| LLM 滚动摘要 | 每轮(或每 N 轮)异步让 LLM 生成累积摘要 | 超长会话质量最好 | 关键路径新增 LLM 调用=新延迟+新故障点;当前会话普遍 <30 轮,收益不抵复杂度。**保留为 >30 轮会话的升级路径**(触发条件:窗口内 brief 条数>8 时再启用) |
| 检索式(嵌入+召回) | 历史向量化按问题召回 | 海量历史 | 严重过度设计 |

## 实现

`frontend/src/state/historyContext.ts`:`compressHistory(messages)` → `[{role, text, fidelity: full|brief}]`;stripMarkdown 剥离表格/代码块/标题/星号强调(**下划线保留**——PLC 标识符 FB_A/i_bEnable 里是常规字符);剥 DeepSeek token 脚注。前端在 chat-ops 与 chat-answer 两条通道的 context.history 携带;后端 `_llm_ops` 与 `build_question_messages` 以 `recent_conversation` 字段注入,系统提示要求:指代性指令必须依据 recent_conversation 展开为具体 ops,步骤缺失则返回空 ops 并说明缺什么,**禁止捏造 UserVar_N 占位变量**;变量命名遵循工程惯例(输入 i_/输出 o_/静态 stat_)。

配套防线:后端 `_normalize_llm_op` 对 `UserVar_N` + 明确 section 的变量自动按惯例改名(用户显式命名的绝不改)。
